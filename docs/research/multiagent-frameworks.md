# Multiagent Framework Landscape

**TL;DR.** As of September 2026, the multiagent framework field has converged on a small set of orchestration topologies — orchestrator-worker/supervisor, explicit graph/workflow execution, peer handoffs, and chat-based group deliberation — and on a small set of generic quality mechanisms: schema-validated structured output (Pydantic/JSON Schema), pass/fail "guardrail" callables with retry, termination-on-approval-signal, manager or LLM-as-judge review, and run-level tracing. Two things nobody ships as first-class primitives are exactly traceagent's specialty: (a) a **pre-validation inter-agent contract** — a structured, machine-checkable acceptance artifact that both producing and consuming agents hold before work is accepted (the pieces exist scattered across CrewAI's `expected_output` + guardrails, OpenAI's handoff input schemas, and A2A's task states, and spec-driven toolkits like Spec Kit and Kiro are contract-first but gate a human-supervised single-agent loop, not agent-to-agent handoff); and (b) **clause-level deliverable↔contract traceability** — a deterministic mapping from contract clauses to deliverable elements, the agent-native analogue of a requirements traceability matrix (ReqIF / IBM DOORS / DO-178C practice). A2A's Task/Artifact envelope gives addressing and provenance, and LangSmith/OpenAI tracing give execution provenance, but neither maps deliverable content to acceptance clauses. That combination is the open niche.

*All facts below are from primary sources (official docs, GitHub repos/code, protocol specs, first-party engineering blogs), fetched 2026-09-03 unless noted. Inferences are explicitly marked.*

## LangGraph (LangChain)

LangGraph is "a low-level orchestration framework and runtime for building, managing, and deploying long-running, stateful agents" — orchestration only, no opinions on prompts or architecture ([overview](https://docs.langchain.com/oss/python/langgraph/overview)). Active as of Sept 2026 (latest monorepo release 2026-08-27, [releases](https://github.com/langchain-ai/langgraph/releases)).

**Key design elements.** Agents and steps are nodes in a `StateGraph` mixing "deterministic, hand-coded steps with LLM-driven agentic steps"; nodes return partial state updates into a shared typed state. Core capabilities: durable execution, persistence/checkpoints ("persisting through failures and resuming long-running work"), human-in-the-loop interrupts where humans "inspect and modify agent state," short/long-term memory, and streaming ([overview](https://docs.langchain.com/oss/python/langgraph/overview); [checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers.md), [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts.md)).

**Multi-agent model.** Canonical pattern is orchestrator-worker: the orchestrator "breaks down tasks into subtasks," delegates via the `Send` API, and workers write outputs "to a shared state key" merged by a reducer (e.g., `Annotated[list, operator.add]`) ([workflows-agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents.md)). Also documented: prompt chaining, parallelization, routing, and an evaluator–optimizer loop where an evaluator grades output and returns improvement feedback that loops back to the generator.

**Contracts/validation/traceability.** Structured output via `with_structured_output` and Pydantic schemas for routing/planning/evaluator grades; programmatic gates can validate intermediate results before the graph proceeds ([workflows-agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents.md)). Validation is any Python predicate inside a node — there is no contract object, no agreed acceptance artifact between nodes, and no deliverable-to-requirement mapping; the nearest traceability analogue is LangSmith observability, which "trace[s] execution paths" and captures state transitions, and LangSmith Engine, which "detects issues in your LangGraph agent traces and proposes fixes" ([overview](https://docs.langchain.com/oss/python/langgraph/overview)).

## AutoGen (Microsoft) and AG2 (fork)

AutoGen is "a programming framework for agentic AI" organized in layers: **Core** ("an event-driven programming framework for building scalable multi-agent AI systems"), **AgentChat** (conversational single/multi-agent apps built on Core), **Extensions** (e.g., `GrpcWorkerAgentRuntime` for distributed agents, `McpWorkbench`), and **AutoGen Studio** for no-code prototyping ([docs index](https://microsoft.github.io/autogen/stable//index.html)). **Status:** not archived, but effectively in maintenance — latest release python-v0.7.5 on 2025-09-30 ([releases](https://github.com/microsoft/autogen/releases)), last repo push 2026-04-15 ([GitHub API](https://api.github.com/repos/microsoft/autogen)); Microsoft's Agent Framework docs call Agent Framework "the next generation of both Semantic Kernel and AutoGen" ([AF overview](https://learn.microsoft.com/en-us/agent-framework/overview/agent-framework-overview)).

**Key design elements.** Multi-agent "teams": `RoundRobinGroupChat` (broadcast turns, shared context), `SelectorGroupChat` (LLM selects next speaker), `MagenticOneGroupChat` (generalist task stack), and `Swarm`, which uses `HandoffMessage` "to signal transitions between agents" ([teams docs](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)). Teams are stateful and resumable; runs return a `TaskResult` with all messages plus a `stop_reason`.

**Contracts/validation/traceability.** The characteristic quality gate is **termination conditions**: composable predicates (`TextMentionTermination`, `ExternalTermination`, `TextMessageTermination`, combinable with `|`) — the docs' own example stops when a critic agent replies "APPROVE," i.e., acceptance-by-conversation-token rather than by machine-checkable contract ([teams docs](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)). There is no schema gate on what an agent must produce to be accepted; traceability is the message log in `TaskResult`.

**The split.** AG2 (repo description: "AG2 (formerly AutoGen)") is the community fork continued by original AutoGen contributors; it markets an "AG2 AgentOS" universal runtime, cross-framework teams (AG2 + Google ADK + OpenAI + LangChain agents), "standardized protocols: A2A and MCPs," and "full decision auditability" as an enterprise outcome ([ag2.ai](https://ag2.ai/), [repo](https://github.com/ag2ai/ag2) — note these are AG2's own claims). Latest release v1.0.3, 2026-08-28 ([releases](https://github.com/ag2ai/ag2/releases)). Inference: the fork is now a small fraction of the original's community (4.9k vs 60.8k stars, GitHub API 2026-09-03), with Microsoft's momentum moved to Agent Framework.

## Microsoft Agent Framework / Semantic Kernel

Microsoft Agent Framework is "the direct successor" to AutoGen and Semantic Kernel, "created by the same teams," combining "AutoGen's simple abstractions for single- and multi-agent patterns with Semantic Kernel's enterprise-grade features such as session-based state management, type safety, filters, telemetry" ([overview](https://learn.microsoft.com/en-us/agent-framework/overview/agent-framework-overview), updated 2026-07-29). Very active: python-1.17.0 released 2026-09-03 ([releases](https://github.com/microsoft/agent-framework/releases)); .NET/Python GA, Go in public preview.

**Key design elements.** Four areas: Agents (including a "Harness Agent" with "planning and todo tracking, context compaction... don't-ask-again tool approval"), **Workflows** ("functional and graph-based workflows that connect agents and functions through explicit execution paths"), and integrations/middleware ([overview](https://learn.microsoft.com/en-us/agent-framework/overview/agent-framework-overview)). The workflow runtime connects typed **executors** through **edges and conditions** with fan-out/fan-in, runs in **supersteps**, and **checkpoints progress at superstep boundaries**; human-in-the-loop is a first-class primitive (`RequestInfoExecutor` in graph mode, `ctx.request_info()` in functional mode); Python additionally offers an experimental functional workflow API ([workflow concepts](https://learn.microsoft.com/en-us/agent-framework/concepts/workflows/)).

**Contracts/validation/traceability.** The graph builder does "type-validated message routing" — an edge-level typing discipline on what flows between components ([workflow concepts](https://learn.microsoft.com/en-us/agent-framework/concepts/workflows/)); middleware intercepts agent actions, and telemetry is an enterprise feature ([overview](https://learn.microsoft.com/en-us/agent-framework/overview/agent-framework-overview)). Semantic Kernel itself remains available ("lightweight, open-source development kit... efficient middleware," v1.0+ non-breaking commitment, [SK overview](https://learn.microsoft.com/en-us/semantic-kernel/overview/)) but is documented via migration guides into Agent Framework ([AF overview](https://learn.microsoft.com/en-us/agent-framework/overview/agent-framework-overview)). No acceptance-contract or clause-mapping concept exists; the analogue is type-checked edges + workflow events/checkpoints as provenance.

## CrewAI

CrewAI is a "framework for orchestrating role-playing, autonomous AI agents" ([repo](https://github.com/crewAIInc/crewAI)); current release 1.15.18 (2026-08-27, [releases](https://github.com/crewAIInc/crewAI/releases)).

**Key design elements.** Agents have roles; work is unitized as **Tasks** with `description` and `expected_output` ("a detailed description of what the task's completion looks like"), `context` (explicit dependency on other tasks' outputs), `human_input`, and `output_file` ([tasks](https://docs.crewai.com/concepts/tasks)). Two processes: `sequential` (output of one task serves as context for the next) and `hierarchical`, which requires a `manager_llm` or `manager_agent` — "tasks are not pre-assigned; the manager allocates tasks to agents based on their capabilities" and oversees "planning, delegation, and validation," including reviewing "outputs, and assesses task completion" ([processes](https://docs.crewai.com/concepts/processes)).

**Contracts/validation — the closest thing to our (a).** CrewAI is the strongest mainstream analogue of contract-first interaction: `expected_output` is a per-task acceptance description the producing agent is graded against, `output_pydantic`/`output_json` make output "not only structured but also validated according to the Pydantic model," and **guardrails** are "function[s] to validate task output before proceeding to next task," returning `(True, validated_result)` or `(False, error_message)`, with failed validation fed back to the agent and retried up to `guardrail_max_retries` (default 3) ([tasks](https://docs.crewai.com/concepts/tasks)). LLM-based guardrails (string descriptions evaluated by the agent's LLM) mix with function guardrails ([tasks](https://docs.crewai.com/concepts/tasks)). **Missing for our (b):** the guardrail is consumer-side code with no persistent artifact; nothing records which clause of `expected_output` which part of the output satisfies — `TaskOutput` exposes `raw`/`pydantic`/`json_dict` and the producing agent, but no clause-level mapping ([tasks](https://docs.crewai.com/concepts/tasks)).

## OpenAI Agents SDK

A Python SDK for multi-agent workflows, "a production-ready upgrade of our previous experimentation for agents, Swarm"; current release v0.22.0 (2026-08-19, [releases](https://github.com/openai/openai-agents-python/releases)). Primitives: **Agents** ("LLMs equipped with instructions and tools"), **handoffs** (delegation), **guardrails** ("validation of agent inputs and outputs"), **sessions** ("persistent memory layer"), and **tracing** ("built-in tracing for visualizing, debugging, and monitoring workflows") ([index](https://openai.github.io/openai-agents-python/)).

**Handoffs as schema-carrying delegation.** "Handoffs are represented as tools to the LLM" (e.g., `transfer_to_refund_agent`). The `handoff()` function supports `input_type` — a Pydantic schema for the handoff tool-call arguments that the SDK "validates... locally" before invoking `on_handoff` — plus `input_filter` to reshape what the receiving agent sees, and `on_handoff` callbacks ([handoffs](https://openai.github.io/openai-agents-python/handoffs/)). Inference: this is the cleanest existing formalization of a *delegation contract* (typed, validated arguments at the moment of transfer), but it constrains the handoff request only — not the returning work product.

**Guardrails as tripwires.** Input guardrails "run only for the first agent in the chain," output guardrails "run only for the agent that produces the final output," and tool guardrails wrap function-tool calls; each returns `GuardrailFunctionOutput` with `.tripwire_triggered`, halting the run with a typed exception. Input guardrails can run in parallel with the agent (default) or blocking ([guardrails](https://openai.github.io/openai-agents-python/guardrails/)). The docs note handoffs stay within a single run, and that there are no prebuilt content guardrails ([guardrails](https://openai.github.io/openai-agents-python/guardrails/)). Function tools get "automatic schema generation and Pydantic-powered validation" ([index](https://openai.github.io/openai-agents-python/)). Scope limits matter for multi-hop design: because guardrails bind to first/last agents only, they cannot express per-hop producer→consumer acceptance criteria without custom wiring — Inference, from the cited scoping rules.

## MetaGPT

MetaGPT ("The Multi-Agent Framework: First AI Software Company") encodes human software-company SOPs: "Code = SOP(Team) is the core philosophy." Assigning roles — "product managers / architects / project managers / engineers" — it takes "a one line requirement as input" and outputs structured artifacts: "user stories / competitive analysis / requirements / data structures / APIs / documents" ([README](https://github.com/FoundationAgents/MetaGPT)). The original paper appeared at ICLR 2024; the team's product line now centers on MGX (Feb 2025) ([README](https://github.com/FoundationAgents/MetaGPT)). Framework releases are stale (v0.8.1, 2024-04-22, [releases](https://github.com/FoundationAgents/MetaGPT/releases)).

**Contracts/validation/traceability.** MetaGPT's distinctive move is exactly our communication medium question: **structured artifacts, not chat, are the inter-agent medium** — each role consumes the previous role's document and produces the next (assembly line). Validation is implicit in SOP sequencing rather than explicit gates; the README describes no schema enforcement or acceptance checking ([README](https://github.com/FoundationAgents/MetaGPT)). Inference: MetaGPT is the closest precedent for "deliverable-as-contract-input" (each artifact constrains the next role), but the artifacts are prose/structured documents with no clause IDs and no satisfaction mapping.

## CAMEL / CAMEL-AI

CAMEL is an open-source community "dedicated to finding the scaling laws of agents," with agents, societies (role-playing, Workforce, OASIS simulation), and design principles of "Evolvability, Scalability, Statefulness, and Code-as-Prompt" ([README](https://github.com/camel-ai/camel)); release v0.2.90 (2026-03-22, [releases](https://github.com/camel-ai/camel/releases)). Its founding contribution is the **role-playing** framework: "we propose a novel communicative agent framework named role-playing," guided by "inception prompting to guide chat agents toward task completion while maintaining consistency with human intentions" ([CAMEL paper, arXiv:2303.17760](https://arxiv.org/abs/2303.17760), NeurIPS 2023 per [README](https://github.com/camel-ai/camel)).

**Contracts/validation/traceability.** Task specification is done up front by `TaskCreationAgent`/`TaskPrioritizationAgent` helpers ([README](https://github.com/camel-ai/camel)); execution is turn-taking dialogue between role-agents (`ChatAgent`s), with `Workforce` for coordinated multi-agent work. There is no acceptance gating or schema enforcement in the cited materials; traceability is conversational. Inference: CAMEL's relevance is the demonstration that role + task-spec prompting steers behavior, but its "contract" lives in prompts, not in checkable artifacts.

## ChatDev and AgentVerse

**ChatDev** ("Communicative Agents for Software Development," arXiv:2307.07924) v1.0 operated "as a Virtual Software Company" (CEO/CTO/Programmer roles); v2.0 ("DevAll"), released 2026-01-07, is "a Zero-Code Multi-Agent Platform" (latest release v2.2.0, 2026-03-23) ([README](https://github.com/OpenBMB/ChatDev), [releases](https://github.com/OpenBMB/ChatDev/releases)). Mechanically, agents communicate "via chat chain" over "sequential phases" — ChatDev "segments the software development process into three sequential phases: design, coding, and testing" — with each subtask executed by an **instructor/assistant** pair in "an automated loop," and a role-flip "dehallucination" mechanism ([paper full text](https://ar5iv.labs.arxiv.org/html/2307.07924)). Verification is two-stage in the testing phase: "code review (static testing) and system testing (dynamic testing)" ([paper full text](https://ar5iv.labs.arxiv.org/html/2307.07924)). Note: the phrase "double verification" often attributed to ChatDev does **not** appear in the paper's full text; the paper's own terms are the two-stage static/dynamic decomposition above. Git-based version control and Docker "safe execution" appear in the README ([README](https://github.com/OpenBMB/ChatDev)).

**AgentVerse** facilitates "the deployment of multiple LLM-based agents," with a **task-solving** framework that "assembles multiple agents as an automatic multi-agent system" and a **simulation** framework for observing agent societies; the paper (arXiv:2308.10848) was accepted at ICLR 2024 ([README](https://github.com/OpenBMB/AgentVerse), [paper](https://arxiv.org/abs/2308.10848)). The abstract claims groups can "dynamically adjust [their] composition" and outperform single agents ([paper](https://arxiv.org/abs/2308.10848)); the README does not document per-task acceptance or schema mechanisms.

## Google A2A Protocol (Agent2Agent)

A2A is "an open standard designed to facilitate communication and interoperability" between independent agents, reusing "existing, well-understood standards (HTTP, JSON-RPC 2.0, Server-Sent Events)"; version **1.0.0** is the latest release, with `spec/a2a.proto` as "the single authoritative normative definition" ([specification](https://a2a-protocol.org/latest/specification/)). Governance: "A2A was originally developed by Google and donated to the Linux Foundation," with a TSC drawing from AWS, Cisco, Google, IBM Research, Microsoft, Salesforce, SAP, ServiceNow; on 2026-08-27 A2A announced it joined the Agentic AI Foundation ([site governance section](https://a2a-protocol.org/latest/), [announcement post](https://a2a-protocol.org/latest/blog/2026/08/27/a-new-chapter-for-a2a-joining-the-agentic-ai-foundation/)); Google's launch post describes it as "an open protocol that complements Anthropic's Model Context Protocol (MCP)" with 50+ launch partners ([Google blog](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/)).

**Object model.** `AgentCard` (self-describing manifest: `name`, `skills`, `capabilities`, `securitySchemes`, `defaultInputModes`/`defaultOutputModes`, ...) enables discovery; a `Task` has `id`, `contextId`, `status`, `artifacts`, `history`, `metadata`; `Message`s carry typed `Part`s ("A Part MUST contain exactly one of the following: text, raw, url, data"); completed work is delivered as `Artifact`s (`artifactId`, `name`, `description`, `parts`) with `TaskArtifactUpdateEvent` streaming ([specification](https://a2a-protocol.org/latest/specification/)). Bindings: JSON-RPC, gRPC, HTTP+JSON/REST, all required to be functionally equivalent ([specification](https://a2a-protocol.org/latest/specification/)).

**Contracts/validation/traceability — the closest protocol-level analogue.** The lifecycle includes consumer-power states: terminal `TASK_STATE_COMPLETED`, `TASK_STATE_FAILED`, `TASK_STATE_CANCELED`, **`TASK_STATE_REJECTED`**, and interrupt `TASK_STATE_INPUT_REQUIRED` ([specification](https://a2a-protocol.org/latest/specification/)). So the protocol lets a client reject a task and demand input — but the spec defines **no acceptance-criteria object, no schema the artifact must satisfy, and no clause mapping**; artifacts have free-text `description`/`metadata` only. Inference: A2A gives us the envelope (task ID ↔ artifact ID provenance) on which a contract layer could ride via `metadata`/extensions.

## Anthropic's multi-agent research system

Anthropic's engineering blog describes a production system using "an orchestrator-worker pattern, where a lead agent coordinates the process while delegating to specialized subagents that operate in parallel" ([blog](https://www.anthropic.com/engineering/built-multi-agent-research-system)). The lead agent saves its plan to Memory, spawns 3–5 subagents in parallel, synthesizes, and iterates; a CitationAgent handles attribution ([blog](https://www.anthropic.com/engineering/built-multi-agent-research-system)).

**Task briefs as proto-contracts.** "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries." Vague briefs caused duplicated/conflicting work — their fix was disciplined brief-writing ([blog](https://www.anthropic.com/engineering/built-multi-agent-research-system)). **Effort scaling** rules allocate resources by complexity ("just 1 agent with 3-10 tool calls" for simple lookups up to "more than 10 subagents" for complex research) ([blog](https://www.anthropic.com/engineering/built-multi-agent-research-system)).

**Verification.** End-to-end quality is evaluated by an **LLM-as-judge rubric** over five criteria (factual accuracy, citation accuracy, completeness, source quality, tool efficiency), with a single LLM call outputting "scores from 0.0-1.0 and a pass-fail grade"; ~20 real queries sufficed to start ([blog](https://www.anthropic.com/engineering/built-multi-agent-research-system)). Production practices: resume from checkpoints, retry logic, "rainbow deployments" ([blog](https://www.anthropic.com/engineering/built-multi-agent-research-system)). Inference: this is the best-documented *organizational* contract practice (written briefs + graded acceptance), but the rubric is a global post-hoc judge, not a per-clause gate on a specific deliverable.

## Model Context Protocol (MCP) — context/tool plumbing (brief)

MCP is "an open-source standard for connecting AI applications to external systems" ([intro](https://modelcontextprotocol.io/docs/getting-started/intro)); current protocol version **2026-07-28**. Client-server architecture (host app creates one client per server), JSON-RPC 2.0 data layer over stdio or Streamable HTTP transport ([architecture](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)). Server primitives: **Tools** (with JSON Schema `inputSchema` per tool), **Resources**, **Prompts**; client primitive: **Elicitation** (server requests user input/confirmation); sampling was deprecated as of 2026-07-28; capability/version discovery via `server/discover` ([architecture](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)). Relevance to contracts: MCP proves the ecosystem accepts **schema-validated, discoverable interfaces** between AI components (`tools/list` + `inputSchema` + validated `tools/call`) — it standardizes the tool boundary, not work-product acceptance between agents.

## GitHub Spec Kit — spec-driven development

Spec Kit is GitHub's open-source toolkit to "Define what to build before building it — with any AI coding agent," where "specifications become executable" and development is "multi-step refinement rather than one-shot code generation" ([README](https://github.com/github/spec-kit)); v1.0.4 (2026-09-02, [releases](https://github.com/github/spec-kit/releases)). Works with "30+ AI coding agents" ([README](https://github.com/github/spec-kit)).

**The gate pipeline.** Slash commands define the loop: `/speckit.constitution` ("project governing principles"), `/speckit.specify` ("requirements and user stories"), `/speckit.clarify` (underspecified areas, "recommended before `/speckit.plan`"), `/speckit.plan`, `/speckit.tasks`, then `/speckit.implement`, with `/speckit.converge` ("Assess the codebase against spec/plan/tasks and append remaining work as new tasks") repeated until **Converged** ([README](https://github.com/github/spec-kit)). Quality gates before implementation: `/speckit.analyze` ("Cross-artifact consistency & coverage analysis") and `/speckit.checklist` (checklists validating "requirements completeness, clarity, and consistency (like 'unit tests for English')") ([README](https://github.com/github/spec-kit)). The repo's templates directory contains `constitution-template.md`, `spec-template.md`, `plan-template.md`, `tasks-template.md`, `checklist-template.md` ([templates/](https://github.com/github/spec-kit/tree/main/templates)).

**Contracts/validation/traceability.** Spec Kit is the purest existing "contract-first" system: the human-agreed spec gates what the agent may implement, and convergence/analyze gates verify the implementation against spec artifacts. But it is a **single-agent, human-supervised** loop: the "contract" is prose markdown agreed with a human, acceptance criteria are not clause-IDed machine-checkable objects, and there is no producer/consumer agent pair negotiating the contract at runtime ([README](https://github.com/github/spec-kit)).

## Amazon Kiro — spec-driven IDE

Kiro (AWS's agentic IDE, launched July 2025) makes specs "structured artifacts that formalize the development process": every spec generates **`requirements.md`** ("user stories, acceptance criteria... in structured notation"), **`design.md`** ("technical architecture, sequence diagrams"), and **`tasks.md`** ("discrete, trackable tasks") ([docs](https://kiro.dev/docs/specs/)). At launch: "Each user story includes EARS (Easy Approach to Requirements Syntax) notation acceptance criteria" ([launch blog](https://kiro.dev/blog/introducing-kiro)). Task execution builds a dependency graph and runs tasks in concurrent waves ("Wave 1 - all tasks with no dependencies. These run concurrently") ([docs](https://kiro.dev/docs/specs/)); the normal workflow has approval gates (only "Quick Spec" can "auto-generate all three artifacts without approval gates") ([docs](https://kiro.dev/docs/specs/)). Agent hooks are event-driven automations on file save/create/delete ([launch blog](https://kiro.dev/blog/introducing-kiro)). Inference: Kiro's requirements→tasks chain is document-level traceability (like a lightweight RTM authored in markdown), but the mapping is by convention in prose, not a deterministic machine-verified index, and again it gates one agent under human approval, not agent-to-agent acceptance.

| **MCP** | Plumbing layer (host–server) | Tools/resources/prompts | JSON-RPC over stdio/Streamable HTTP | JSON Schema `inputSchema` on tools | Elicitation confirmations | Notifications/progress (logging deprecated) |
| **GitHub Spec Kit** | Command-gated pipeline (human-supervised agent) | Phases: specify→plan→tasks→implement | Markdown artifacts in repo (`specs/`) | Prose spec + acceptance criteria; templates | `/speckit.analyze` cross-artifact check; `/speckit.checklist`; `/speckit.converge` | Git (artifacts are files) |
| **Kiro** | Spec-gated workflow (single agent + human approvals) | 3 artifacts; task waves | `requirements.md` / `design.md` / `tasks.md` | EARS-notation acceptance criteria | Approval gates between phases; hooks | Task status UI; dependency waves |

**Recurring primitives across frameworks:**

1. **Four topologies keep reappearing.** Orchestrator-worker/supervisor (LangGraph, Anthropic, CrewAI hierarchical, Agent Framework workflows), explicit graphs with typed edges (LangGraph, Agent Framework), peer handoff (OpenAI SDK, AutoGen Swarm), and chat deliberation (AutoGen group chat, CAMEL, ChatDev, AgentVerse). Interoperability protocols (A2A) and plumbing (MCP) sit outside all four.
2. **Pydantic/JSON Schema is the universal schema mechanism** — but it is applied at *tool calls* and *node/model I/O* (LangGraph, CrewAI, OpenAI SDK, MCP, Agent Framework), never as an *acceptance contract on a work deliverable* that both parties hold.
3. **Quality gates are generic predicates, not contracts.** Every framework reduces validation to "a callable (or LLM judge) that returns pass/fail plus feedback, with retries" — CrewAI guardrails, OpenAI tripwires, AutoGen termination conditions, LangGraph evaluator nodes, Anthropic's judge rubric. None of them requires the gate to be *mutually agreed before work starts*, and none versions it.
4. **Two traceability idioms exist, and both are weak.** Execution tracing (LangSmith, OpenAI tracing, Agent Framework telemetry, AutoGen's `TaskResult`) answers "what happened," not "which requirement did this satisfy." Spec-driven artifacts (Spec Kit, Kiro, MetaGPT) encode intent in markdown but leave the requirement→implementation mapping implicit and human-verified.
5. **Communication is converging on structured envelopes with free-text payloads.** A2A types the envelope (`Task`, `Artifact`, `Part`) and leaves content to `Part`s; frameworks that made artifacts the medium (MetaGPT) or briefs explicit (Anthropic) report better coordination — evidence that structure in the medium, not just the transport, pays off.

## Gap Analysis vs. Our Specialty

**(a) Contract-first interaction (pre-validation inter-agent contracts).** Partially exists, in fragments:

- *Closest analogues:* CrewAI's `expected_output` + `output_pydantic` + **guardrails** is the nearest full pipeline — a declared expectation, a schema-validated output, and a pass/fail gate with bounded retries before the next task proceeds ([tasks](https://docs.crewai.com/concepts/tasks)). OpenAI's handoff `input_type` formalizes the *delegation* moment with validated structured arguments ([handoffs](https://openai.github.io/openai-agents-python/handoffs/)). A2A provides consumer-side rejection (`TASK_STATE_REJECTED`) and clarification (`TASK_STATE_INPUT_REQUIRED`) states in the task lifecycle ([specification](https://a2a-protocol.org/latest/specification/)). Anthropic's subagent brief format (objective, output format, boundaries) is the best-documented *practice* of stating acceptance before work ([blog](https://www.anthropic.com/engineering/built-multi-agent-research-system)).
- *What's missing:* No framework treats the acceptance criteria as a **negotiated, structured, versioned artifact that both producer and consumer reference by ID**. CrewAI's expectation lives in one task object and its guardrail is consumer-side code; OpenAI's schema covers the request, not the deliverable; A2A has no acceptance-criteria object; Spec Kit/Kiro are contract-first but only between a human and one agent (prose specs, human approval gates). Nothing enforces "work is not valid until each contract clause is satisfied by named evidence" as a framework invariant.

**(b) Deliverable-to-contract traceability (clause-level).** Essentially absent:

- *Closest analogues:* A2A's `Task.artifacts` gives a deterministic envelope-level linkage (task ID ↔ artifact ID ↔ parts) — the right *shape*, with no clause semantics ([specification](https://a2a-protocol.org/latest/specification/)). Kiro's requirements→design→tasks chain and EARS acceptance criteria give document-level intent traceability in markdown, with tasks as "discrete, trackable" units ([docs](https://kiro.dev/docs/specs/)); Spec Kit's `/speckit.analyze` performs "cross-artifact consistency & coverage analysis" — an audit pass, not a persistent, machine-checked matrix ([README](https://github.com/github/spec-kit)). Execution tracing (LangSmith, OpenAI, Agent Framework telemetry) links spans to run structure, not to acceptance clauses.
- *The regulated-practice analogue we should name:* requirements traceability matrices are institutionalized in safety-critical engineering — requirements interchange is standardized as ReqIF 1.2 (OMG, 2016, built with automotive/IBM/PTC input to "exchang[e] requirements data between organizations") ([OMG](https://www.omg.org/spec/REQIF/)); IBM's DOORS line markets "AI-assisted requirements management for traceable and compliant product development" with "customizable requirements views with multi-level traceability" ([IBM](https://www.ibm.com/products/requirements-management)); DO-178C is published by RTCA for airborne software ([RTCA](https://rtca.org/products/do-178c/)), and ISO 26262 governs automotive functional safety ([ISO 26262-1:2018](https://www.iso.org/standard/68383.html)). Inference: these regimes require bidirectional, evidence-backed trace links (requirement ↔ design ↔ code ↔ test) maintained as a first-class artifact — exactly the discipline no agent framework reproduces, and exactly what "deliverable-to-contract traceability" would port into agent-native form.

**Net gap for traceagent.** The industry has (1) schema enforcement at tool/model boundaries, (2) generic pass/fail gates with retry, (3) spec-gated single-agent pipelines with human approvals, and (4) envelope-level task↔artifact linkage (A2A). It lacks a **contract object** (structured acceptance criteria, agreed by both agents before execution, with IDs and versions) and a **trace matrix artifact** (deterministic clause→deliverable-element mapping, machine-checkable, produced with the deliverable and required for acceptance). CrewAI's guardrail-with-retry loop, OpenAI's typed handoffs, A2A's task/artifact lifecycle, and Kiro/Spec Kit's EARS-and-checklist gating are the four interface points a contract-first, traceability-native layer could standardize over — Inference, synthesized from the sources above.
